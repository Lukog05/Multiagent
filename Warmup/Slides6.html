The Hospital Domain

Problem Description

Environment Elements

  • Walls Obstacles (black squares)
  • Agents Robots (colored numbered circles: 0, 1, 2...)
  • Boxes Items to transport (colored lettered squares: A, B, C...)
  • Goals Target positions (yellow circles/squares)

Grid-based, turn-based environment inspired by hospital robots (TUG) and warehouse systems (Amazon KIVA).

Key Constraints

  • Color matching: Agents can only move boxes of the same color
  • Goal test: Each goal cell must have the correct object (agent or box) on it
  • Joint actions: All agents act simultaneously each timestep
  • Conflicts: Agents cannot occupy same cell or swap positions

Multi-Agent Path Finding (MAPF) Subset

Exercises 1–4 focus on MAPF levels: no boxes, only agents finding paths to their goal positions. This simplifies the problem to pure coordination without box manipulation.

Search Client Architecture

High-Level Execution Flow

1. Parse level file → create initial State
    2. Choose search strategy (Frontier + Heuristic)
    3. GraphSearch.search(initialState, frontier, heuristic)
    4. Extract solution plan (sequence of joint actions)
    5. Send actions to server, receive feedback

Core Components

  • SearchClient Main orchestrator, parses level
  • State Stores agent positions, walls, goals; generates successors
  • Action Defines NoOp, Move(N/S/E/W) (Push/Pull in Ex5+)
  • GraphSearch Generic search loop (frontier + explored set)
  • Frontier Strategy-specific container (Queue/Stack/PriorityQueue)
  • Heuristic Provides h(s) for informed search

Graph-Search Algorithm (Generic)

Pseudocode

function GRAPH-SEARCH(initial, frontier):
        frontier.add(initial)
        explored ← ∅

        while frontier is not empty:
            node ← frontier.pop()

            if GOAL-TEST(node):
                return EXTRACT-PLAN(node)

            explored.add(node)

            for each action in ACTIONS(node):
                child ← RESULT(node, action)

                if child ∉ explored and child ∉ frontier:
                    frontier.add(child)

        return failure

Frontier Strategies

  • BFS Queue (FIFO) → explores by increasing depth
  • DFS Stack (LIFO) → explores deep branches first
  • Best-first PriorityQueue (ordered by f(n)) → explores most promising states
Exercise 2

Breadth-First Search (BFS)

Implementation

  • Frontier: Queue (FIFO)
  • Expansion order: Level-by-level (depth d, then d+1, ...)
  • Completeness: Yes (finite branching + solution exists)
  • Optimality: Yes (unit step costs)

Complexity Analysis

  • Time: O(b^d) where b = branching factor, d = solution depth
  • Space: O(b^d) – stores entire frontier layer
  • Problem: Exponential memory usage for MAPF
  • Branching factor: ~5^A for A agents (NoOp + 4 moves each)

Exercise 3

Depth-First Search (DFS)

Implementation

  • Frontier: Stack (LIFO)
  • Expansion order: Dive deep into one branch before backtracking
  • Completeness: No (infinite paths possible)
  • Optimality: No (returns first solution found)

Complexity Analysis

  • Time: O(b^m) where m = maximum depth
  • Space: O(bm) – only stores path + siblings
  • Advantage: Much lower memory usage
  • Trade-off: Can find very long solutions

When does DFS outperform BFS?

  • Memory-constrained scenarios: DFS succeeds where BFS runs out of memory
  • Deep solution paths: If solution is deep anyway, DFS may stumble upon it faster
  • Lucky branching: If correct branch is explored first, DFS finds solution quickly
  • Caveat: Solution length typically much worse (10x–100x longer plans)

Exercise 4

Best-First Search Framework

Core Idea

Use a priority queue frontier ordered by an evaluation function f(n) to guide search toward promising states.

f(n) = evaluation function combining:
      - g(n) = path cost from initial to n
      - h(n) = heuristic estimate from n to goal

Search Variants

  • Greedy f(n) = h(n) – expand state closest to goal (by heuristic)
  • A* f(n) = g(n) + h(n) – optimal if h is admissible
  • Weighted A* f(n) = g(n) + w·h(n) – trades optimality for speed (w > 1)

Properties

  • Admissible h: h(n) ≤ true cost → A* optimal
  • Consistent h: h(n) ≤ c(n,n') + h(n') → efficient A*
  • Greedy: Fast but not optimal
  • Key insight: Good h(n) dramatically reduces search space
Exercise 4

Heuristic 1: Goal Count

Mathematical Definition

h_goalCount(s) = |{ agent i : position(i) ≠ goal(i) }|

Simply counts how many agents are not on their goal positions.

Properties

  • Admissible: Yes (at least one action per misplaced agent)
  • Computation: O(A) – very fast
  • Informativeness: Low – ignores distances and obstacles
  • Problem: Creates large "plateaus" where many states share the same h-value

Expected Behavior

  • Greedy: Prefers states with fewer misplaced agents
  • A*: Balances depth (g) with progress (h)
  • Issue: Doesn't distinguish between agents 1 step away vs 100 steps away
  • Result: Often similar to BFS performance

Goal Count – Performance Analysis

Comparison to Uninformed Search

  • MAPF01: A* expands 2,303 states (same as BFS), but faster runtime (0.20s vs 0.79s)
  • MAPF02C: Greedy reduces expansions by ~50% (101k → 46k) and time by ~50% (32s → 17s)
  • Sliding puzzle: Greedy dramatically better (81k → 426 expanded), but longer plan (28 → 46 actions)
  • Hard levels: Still timeout on MAPF03, MAPFreorder2

Why These Results?

  • Limited guidance: GoalCount doesn't capture distance → many h-plateaus
  • A* ≈ BFS: When h-values are similar, g(n) dominates → depth-first ordering
  • Greedy wins sometimes: Commits to h-improving states → faster but suboptimal
  • Coordination ignored: Doesn't model agent conflicts → fails on tight-coupling levels

Key Insight

Goal Count provides minimal guidance – it's barely better than uninformed search. We need a heuristic that captures distance and obstacles.

Exercise 4

Heuristic 2: Distance-Sum (Preprocessed)

Mathematical Definition

Preprocessing (once per level):
      For each free cell c:
        dist[c][goal] = BFS shortest path from c to goal
        (accounting for walls)

    Runtime heuristic:
      h_distSum(s) = Σ_{i=1}^{A} dist[position(agent_i)][goal(agent_i)]

Sums up the obstacle-aware shortest-path distance for each agent to its goal.

Properties

  • Admissible: Yes (ignores agent-agent conflicts → underestimates)
  • Computation: O(A) per state after O(|cells|²) preprocessing
  • Informativeness: Much higher – captures distance + obstacles
  • Gradient: Moving toward goal decreases h(s)

Implementation Notes

  • Run BFS from each free cell to compute distances to all other cells
  • Store results in dictionary: distances[(row,col)][(goal_row,goal_col)]
  • Lookup is O(1) per agent during search
  • Can reuse table across multiple search runs on same level
Exercise 4

Distance-Sum – Intuition & Trade-offs

What It Estimates

  • Approximates remaining solution length as sum of individual shortest paths
  • Creates a useful gradient: moving toward goal → lower h(s)
  • Accounts for walls and obstacles (unlike Goal Count or Manhattan distance in wall-free grids)
  • Lower bound on true cost (ignores coordination overhead)

Strengths ✓

  • Much more informative than Goal Count
  • Dramatically reduces expansions on many levels
  • Fast evaluation (after preprocessing)
  • Works well with Greedy and A*

Weaknesses ✗

  • Ignores agent-agent interactions (collisions, blocking)
  • Underestimates coordination-heavy levels
  • Can still fail on "reorder"-type puzzles
  • Preprocessing cost for very large levels

Improved Heuristic Design

Goal

Design stronger heuristic h'(s) for Sokoban domain

Components

  • Box → Goal distance: Sum of Manhattan distances
  • Agent → Nearest box: Positioning cost
  • Deadlock detection: Corner & wall deadlocks
  • Box penalty: Encourages faster solutions
h(s) = Σ dist(box_i → goal_i) 
     + min(dist(agent → box_j))
     + penalty × num_boxes
